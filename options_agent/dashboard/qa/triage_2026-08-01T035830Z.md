## QA-001 — No distinct lockout message

**Verdict:** CONFIRMED (partially mis-described) → FIXED

**Reproduction commands & result:**
```bash
# Start QA instance, then:
for _ in range(4):  # 4 attempts needed; max_login_attempts=3, LoginError fires on attempt N+1
    login(page, "qa_member", "wrong-again")
```
The QA report said users see "Invalid username or password." at lockout. The underlying truth
is worse: the model raises `LoginError('Maximum number of login attempts exceeded')` on the
**(max + 1)th** attempt, which propagated unhandled through `Authenticate.login()` and
`require_auth()`, causing a Streamlit exception traceback. With exactly 3 attempts (as the
QA report ran), `authentication_status` is `False` and the wrong-password path fires —
matching what the report observed. Four attempts reveals the unhandled exception.

**Security tradeoff analysis:**

Option (a) NOT_A_BUG is not viable — an unhandled exception traceback is both worse UX
and potentially an information-disclosure vector (stack frames, module paths).

Option (b) is chosen: catch `LoginError` in `require_auth()` and show a generic
**time-based** message ("Too many failed attempts. Please wait a few minutes and try
again.") that:
- Does NOT confirm the account exists (no user enumeration).
- Does NOT reveal lockout status for a given username (avoids confirming a valid target).
- Is indistinguishable from rate-limiting to an attacker.
- Preserves the existing fail-closed, generic-errors security posture.

**Fix:** `/tmp/oat-auth/options_agent/dashboard/_auth.py`

1. Import `LoginError` from `streamlit_authenticator.utilities.exceptions`.
2. Wrap `authenticator.login(...)` call in `require_auth()` with `try/except LoginError`.
3. Catch block calls `_persist_failed_login()` (same as wrong-password path), then
   `st.error("Too many failed attempts. Please wait a few minutes and try again.")`,
   then `st.stop()`.

**Verification:**
- Browser test: 4 × wrong attempts → "Too many failed attempts..." message, no traceback, not logged in. [PASS]
- AppTest: unit-level injection confirms `LoginError` is catchable without exception propagation. [PASS]
- New regression check added: `lockout: shows too-many-attempts message (no traceback)` in browser suite.

## OBS-001 — Signup success message below the fold

**Verdict:** CONFIRMED → FIXED

**Reproduction:** Sign up via invite link with a long form. `st.success()` rendered at
the bottom of the invite form, below the fold. `st.query_params.clear()` cleared the URL
but did not reload the page, so the user had to scroll down to see the confirmation.

**Security note:** No security concern. The invite was already validated before rendering
the form.

**Fix:** `/tmp/oat-auth/options_agent/dashboard/_auth.py` — `_handle_invite()`:

Replaced:
```python
st.success("✅ Account created. Remove the invite link from the address bar and sign in.")
st.query_params.clear()
```
With:
```python
st.query_params.clear()
st.rerun()  # invite param is gone; page reloads showing the login form
```

`st.rerun()` after `st.query_params.clear()` reloads the page without the `?invite=`
param, so the user lands on the login form at the top — cleaner than a success banner
below the fold and removes the "remove the link from the address bar" instruction since
`query_params.clear()` already does it.

**Verification:** `signup: no visible traceback` browser check [PASS]; the signup flow
completes and the invite token is consumed (OBS-003 reused-invite test confirms this).

## OBS-002 — Sidebar nav visible to unauthenticated users

**Verdict:** NOT_A_BUG / WON'T-FIX

**Reproduction:** `01_gate.png` — sidebar shows "app" / "Admin" page labels before auth.

**Rationale:** This is Streamlit platform behavior — the sidebar is rendered by the
framework before `st.stop()` gates the page. Browser test `01_gate` confirms clicking
those links hits the gate and no protected content is leaked. The sidebar shows only
*page names* (not any fund P&L data), which is not sensitive. Fixing this would require
restructuring to a single-page app or hiding the sidebar with custom CSS — a framework
limitation, not a defect.

**Fix:** None.

## Escalation

**None.** QA-001 option (b) — generic time-based message — was selected as the
security-safe resolution. No product-design decision required from the human. The message
"Too many failed attempts. Please wait a few minutes and try again." is neutral with
respect to account enumeration. If the fund owner wants a *shorter* or *branded* version
of that text in the future, it can be changed without security risk.
